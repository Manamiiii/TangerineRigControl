## 1. 结论与问题总览

工程规模较小，分层基本清楚，没有必要重写、引入通用自动化框架或恢复控件名称识别。应保留已经实测有效的坐标录制、配置草稿隔离、点击前窗口保护及“显卡先、华硕后”的顺序。

当前主要风险集中在两处：**异常配置的保护不足**，以及 **Aura COM 调用与应用退出之间缺少可靠的生命周期边界**。其次是四软件入口适配、等待/取消流程、启动项和文档不一致。单纯删除旧字段、整理格式不能解决这些问题。

| --- | --- | --- |
| P0 | Q01 配置回退与备份；Q02 SDK 卡住影响退出 | 首批，先保护已有录制及退出能力 |

## 3. 分类明细

以下路径相对于工程根目录，行号以本轮审查的工作树为准。

### A. 配置与数据保护

#### Q01｜高｜任一配置错误导致整份回退，后续保存会滚掉唯一备份

- **位置：** `src/TangerineRigControl/Infrastructure/SettingsStore.cs:59`、`:77`、`:93`。
- **证据与影响：** 四组配置统一反序列化、统一校验；一条序列的无效坐标或空 Steps 就会进入 catch，把全部设置换成默认值。启动有警告，并非静默；但没有尝试读取 `.bak`，也没有区分正常设置和“读取失败后的默认草稿”。用户保存时仍可覆盖原文件，且每次 `File.Replace` 都更新同一个 `.bak`。若主文件损坏但备份完好，第一次保存会用损坏文件替换好备份；后续保存还可能丢掉最后可供人工恢复的版本。
- **建议：** 将加载结果与错误状态显式返回；优先验证已有备份；恢复前保留不覆盖的故障副本；禁止普通保存流程把故障回退当作正常编辑。能可靠隔离的单组校验错误保留其他组，并说明受影响组。不要自动清空重录。
- **验证：** 主文件坏/备份好、单组坏、两者都坏、连续保存、写入失败等临时目录用例，检查原始字节和正常组序列仍可恢复。

#### Q03｜中｜旧配置缺少 SDK 标志时会直接启用新的控制后端

- **位置：** `src/TangerineRigControl/Models/RigSettings.cs:29`；`Infrastructure/SettingsStore.cs:67`；`UI/MainForm.cs:294`。
- **证据与影响：** 构造函数把 `UseAuraSdk` 设为 true，XML 未包含该字段时仍为 true。因此已有华硕录制的旧配置也会改走 SDK，其关灯、恢复默认灯效和退出释放语义与录制不同。该行为符合当前“默认 SDK”代码意图，但缺少可区分的新安装/迁移策略。
- **建议：** 明确旧版本迁移策略和配置版本；不要仅靠构造函数默认值切换旧用户的已有后端。新安装默认值与升级迁移分开定义，并保留现有录制。

#### Q17｜中｜等待时间校验、默认填充和执行规则互相矛盾

- **位置：** `Infrastructure/SettingsStore.cs:52`、`:137`；`Automation/MacroRunner.cs:23`、`:32`（均位于 `src/TangerineRigControl/`）。
- **证据与影响：** 校验允许启动等待 0，但默认填充把 0 改为 1200；回放又强制启动等待至少 300、步骤等待至少 100。合法配置不会按其保存值执行。0→1200 已用内存用例复现。
- **建议：** 统一最小值与默认规则；区分“缺失”和“显式填写 0”，或直接校验拒绝低于支持范围的值；迁移只补缺失字段。

#### Q18｜中｜启动时会覆盖暂时不可用的用户程序路径

- **位置：** `src/TangerineRigControl/Infrastructure/SettingsStore.cs:114`；`Infrastructure/InstalledAppLocator.cs:35`。
- **证据与影响：** 用户配置路径一旦 `File.Exists=false`，加载就用自动发现结果或空字符串替换它；下一次保存会持久化该替换。磁盘暂不可用、安装中或权限变化都可能丢失原选择。自动发现还把 `DisplayIcon` 当启动程序，未确认它确实是主入口。
- **建议：** 保留已有路径并显示不可用；只为空路径提供发现结果。图标路径只能作为候选，至少校验扩展名和已知入口，注册表访问失败应局部降级，避免在 Load 的异常处理之外中断启动。

### B. Aura SDK 与任务生命周期

#### Q02｜高｜SDK 调用无时间边界，退出在 UI 线程等待同一把锁

- **位置：** `src/TangerineRigControl/Services/AuraLightingClient.cs:20`、`:103`；`UI/MainForm.cs:155`。
- **证据与影响：** `SetEnabled` 在 `_gate` 内同步调用外部 COM；取消只在调用之间检查。`MainForm.Dispose` 在 UI 线程调用 `_aura.Dispose()`，后者也取 `_gate` 并同步释放 COM。若厂商调用不返回，停止无效，退出还会卡住界面。这是故障路径风险，本轮未对硬件制造挂起。
- **建议：** 明确 SDK 会话所有者、关闭状态和等待上限；UI 退出不应同步等待未知时长 COM。只给 Task 加超时不能终止底层调用，超时后不可宣称已经释放控制权。先修 UI 生命周期；若要求挂死也能可靠回收，见“新功能/较大重构建议”的隔离方案。
- **验证：** 使用可阻塞的 SDK 替身测试关闭、取消、重复退出和超时后禁止重入，不用真实设备制造异常。

#### Q04｜中｜取消 SDK 选项会新建 SDK 会话，而不只是释放已有会话

- **位置：** `src/TangerineRigControl/UI/MainForm.cs:93`；`Services/AuraLightingClient.cs:28`。
- **证据与影响：** 取消 SDK 选项后调用 `SetEnabled(true)`；如果此前没有会话，该方法仍创建 SDK、调用 `SwitchMode`，然后释放。没有安装 SDK 的用户仅想改用录制，也可能在设置已保存后收到 SDK 失败；有 SDK 时则发生一次不必要的全局控制权切换。
- **建议：** 提供只释放现存会话的内部方法；无会话直接返回。设置保存结果和会话释放失败分别呈现，不把两者混成“保存失败”。

#### Q07｜中｜窗口等待流程没有传递取消令牌，名义超时不是总耗时上限

- **位置：** `src/TangerineRigControl/Infrastructure/ExternalAppController.cs:14`、`:132`、`:145`；`Infrastructure/LConnectWindowRestorer.cs:38`；`Automation/MacroRunner.cs:19`。
- **证据与影响：** 启动、找窗口、恢复、前台等待及最小化使用同步调用/固定 sleep，不接收操作 token。点击“停止”后仍可能启动、恢复或收起窗口；10 秒计时在启动进程之后才开始，内部恢复/UIA 也可能超过这个上限。
- **建议：** 让整个流程共享取消令牌和剩余时间预算，检查每次有副作用操作前的取消；可替换的 sleep 使用可取消等待。对无法中断的系统调用明确限制，避免承诺绝对及时停止。

#### Q13｜中｜SDK 关键错误原因被包装丢失，释放失败被完全吞掉

- **位置：** `src/TangerineRigControl/Services/AuraLightingClient.cs:73`、`:77`、`:94`。
- **证据与影响：** “未识别到设备”等明确错误最终只显示异常类型；`TryRelease` 吞掉全部释放失败。`Release` 在调用 `ReleaseControl` 前就把字段清空，失败后失去可追踪的会话状态。用户无法区分未安装、未找到设备和释放失败。
- **建议：** 定义少量脱敏错误类别，保留受控业务错误和 HRESULT；将释放结果反映在状态中。避免输出未经处理的厂商异常正文或本机路径，也不要盲目重试有副作用的操作。

#### Q14｜中｜SDK 只控制到一种设备也按整组执行完成

- **位置：** `src/TangerineRigControl/Services/AuraLightingClient.cs:37`、`:64`；`UI/MainForm.cs:300`；`UI/SettingsForm.cs:48`。
- **证据与影响：** `deviceCount>0` 即通过，不能区别只识别主板还是只识别内存；开启则切换/释放而不枚举。主界面虽谨慎写了“实际状态待确认”，仍没有报告这组中的哪些设备被发现。SDK 关闭需保持进程存活、退出可能亮灯等语义只在 README 中说明，主界面“开启/关闭”看不出区别。
- **建议：** 反馈已识别类别和未识别类别，避免把存在一个 ARGB 项等同主板与内存都已覆盖；在 SDK 选项附近说明恢复默认灯效及退出释放语义。不为检测状态而额外获取硬件控制权。

### C. 录制、窗口适配与输入

#### Q05｜中｜录制没有记录实际等待时间，也没有调整等待时间的界面

- **位置：** `src/TangerineRigControl/Automation/MacroRecorderForm.cs:153`；`Models/RigSettings.cs:96`；`docs/NIGHTLY-DEVICE-TEST.md`“单项验证”后的等待说明。
- **证据与影响：** 每步只写坐标，等待统一为默认 900ms；录制时手动等几秒不会被保存。文档要求慢页面增加等待，但设置页没有入口。慢机器或页面重载时容易在下一页未准备好时点击。
- **建议：** 最小修复先把界面及文档写清楚实际固定等待，并给出当前支持的配置方法。若要可视化调整每步等待，作为单独小功能实施；不以恢复控件识别替代坐标方案。

#### Q06｜中｜“打开原厂软件”和开始录制会阻塞 UI

- **位置：** `src/TangerineRigControl/UI/MainForm.cs:339`；`UI/SettingsForm.cs:182`；`Automation/MacroRecorderForm.cs:95`。
- **证据与影响：** 这些事件在 UI 线程调用含轮询、sleep、进程启动及 UIA 的方法，数秒内无法操作窗体。`BeginInvoke(StartRecording)` 只是延后执行，并没有移出 UI 线程。
- **建议：** 异步执行等待部分，明确打开中状态、防止重复点击，取消和关闭时收尾；涉及 UIA 的线程/COM 使用方式须单独验证，不机械地把所有代码包进 Task.Run。

#### Q08｜中｜将 EXE 文件名等同窗口进程名，无法表达启动器与真实进程的区别

- **位置：** `src/TangerineRigControl/UI/SettingsForm.cs:157`、`:202`；`Infrastructure/ExternalAppController.cs:83`。
- **证据与影响：** 新增灯光组的 `ProcessName` 总从所选 EXE 推导。若入口是 bootstrapper，实际窗口属于另一个进程，就会“软件已打开却找不到窗口”。仅 EXE 的选择模型也没有应用标识启动方式。当前用户机器每个入口是否触发该问题仍需针对所选入口确认。
- **建议：** 将启动入口与窗口识别分别建模，为当前已授权的两款灯光软件做有限适配；不扩展成任意软件自动化框架。新增应用标识启动支持的范围见后文。

#### Q09｜中｜新灯光组未具备与两块屏幕等价的托盘恢复能力

- **位置：** `src/TangerineRigControl/Models/RigSettings.cs:33`；`Infrastructure/ExternalAppController.cs:113`、`:54`；`Infrastructure/LConnectWindowRestorer.cs:13`。
- **证据与影响：** 两个新组默认无标题筛选，隐藏窗口被过滤；特殊恢复仅覆盖 KANALI 和 L-Connect。新组依赖再次启动 EXE 恰好能唤醒窗口，不能从现有屏幕验收推出它们也兼容隐藏/托盘状态。
- **建议：** 对当前两款软件分别验证首次启动、普通最小化、隐藏到托盘；只为失败的状态添加有证据的恢复方式。找不到窗口时不继续点击。

#### Q10｜中｜更换软件路径不提示已有坐标可能失效，窗口身份仅凭进程名筛选

- **位置：** `src/TangerineRigControl/UI/SettingsForm.cs:155`、`:202`；`Infrastructure/ExternalAppController.cs:71`。
- **证据与影响：** 路径更改后原坐标仍原样保留；对于灯光组，进程名又随新 EXE 变更，因此会对新软件回放旧坐标。候选窗口也未核对配置的可执行身份，同名进程或同进程多个窗口可能选中非预期界面。
- **建议：** 不删除旧录制；路径变更后标明需复核再执行，记录/核对目标身份。窗口核对失败应明确拒绝。维持坐标回放，不增加按钮名称识别。

#### Q16｜中｜最后一次点击主动收起窗口会被当成回放失败

- **位置：** `src/TangerineRigControl/Automation/MacroRunner.cs:40`、`:44`。
- **证据与影响：** 所有点击结束后仍强制要求原窗口可见且处于前台；若最后录制的是关闭页面、原厂应用自动隐藏，或完成后焦点自然变化，实际动作可能已完成，却报“窗口已变化”，而非说明收尾状态。此路径与用户曾问“能否录制关闭页面”直接相关。
- **建议：** 将“后续还要点击”的严格前置保护与“最后一步完成后的收尾检查”分开；保留中途前台/遮挡检查。明确界面是否支持把收起录入最后一步，不用同一异常描述所有阶段。

### D. 启动项与 UI/UX

#### Q11｜中｜没有 Run 注册表键时，连不启用自启动的普通保存也会失败

- **位置：** `src/TangerineRigControl/Infrastructure/StartupManager.cs:12`、`:28`；`UI/SettingsForm.cs:87`。
- **证据与影响：** `ReadValue/SetEnabled` 均要求键已存在；设置每次保存都调用这两步。新用户配置或键被删除时，即使仅保存录制、且未勾选自启动，也被拒绝。
- **建议：** 缺键读取视为无启动项，关闭时无键直接成功，只有启用时创建键；没有变更时不写注册表。测试采用替代存储，不修改用户真实 Run 项。

#### Q12｜中｜登录启动不满足管理员权限要求，且状态判断只检查值是否存在

## 5. 可执行修改步骤与验收

### 阶段 1：保护配置，建立最小故障回归（Q01、Q03、Q17、Q18、Q21）

1. 保留当前所有未提交改动；实施前把真实设置及备份保存在本机忽略目录，禁止进仓库。
2. 将 XML 解析/迁移/校验与实际文件位置分开，使临时目录可测；不改变坐标格式。
3. 增加载入结果和恢复保护，落实备份策略；修正默认值与路径覆盖行为。
4. 用两屏已有步骤、缺灯光组、非法单组、损坏主文件、好备份、重复保存、写失败等夹具验证。
5. 验收：有效屏幕序列逐项一致，异常不会因普通保存而毁掉可恢复版本；草稿取消不改变磁盘。

### 阶段 2：修正 SDK 会话与退出（Q02、Q04、Q13、Q14）

1. 为 SDK 建最小接口替身，定义未连接、持有、释放失败等状态及所有者。
2. 禁用选项只释放已有会话；分开业务操作结果与释放结果。
3. 改造退出等待，避免 UI 线程同步等待外部 COM；明确无法中断调用的限制。
4. 测试未安装、零设备、部分类型、调用失败、取消、释放失败和挂起替身。
5. 验收：无会话时关闭 SDK 不触发新 COM 调用；所有失败都能给出准确状态，且没有未经验证的“已释放”声明。

### 阶段 3：稳定现有交互与四软件入口（Q05–Q12、Q15–Q16、Q19–Q20）

1. 取消令牌与截止时间贯穿恢复/等待；把长等待移出 UI 事件同步路径。
2. 区分启动入口和窗口身份，为现有四软件逐个核对，保留原坐标和严格中途检查。
3. 修复启动项缺键保存，明确权限限制与手动启动语义。
4. 调整收尾检查、忙碌状态、结果展示及已有布局；先修文案，再决定是否添加等待编辑功能。
5. 助手先做合成窗口与替身测试；必要实机验收才让用户观察灯光/屏幕，操作 UAC。

### 阶段 4：收敛维护与发布（Q22–Q29）

1. 合并少量重复流程，整理命名/using/格式；兼容字段先保留。
2. 更新 README、测试清单、调查文档；分开当前使用与历史验收。
3. 标准工具链构建，CI 增加明确超时与命名测试输出。
4. 核实本地启动入口后统一发布位置，记录构建标识；再清理确认不再引用的实验产物。
5. 最终检查 diff 和暂存清单，仅包含源码、合法资源和文档；提交/推送及清理应在对应实施授权范围内执行，本轮没有执行。

**必要实机检查（后续修复完成才需要）：** 从最终桌面入口打开，确认两块屏幕的开启/关闭步数与保存前一致；取消设置重开后不变；四软件分别在未运行、最小化、托盘隐藏时可进入正确界面；执行全部操作时显卡先于华硕；SDK 关闭/开启及退出后的灯效符合提示。

## 6. 新功能建议 / 需要单独划定范围的重构

以下不是本轮已实施内容，也不是清理工程的前置要求。

| 建议 | 理由 | 范围判断 |
| --- | --- | --- |
| 每步等待时间的小型编辑入口 | 解决慢页面问题，让文档的调整步骤可实际执行 | 小功能；不恢复控件识别、不增加自动状态猜测 |
| SDK 工作进程隔离 | 外部 COM 真正挂死时，进程内 Task 超时无法安全取消 | 较大重构；只有要求强故障隔离时再做，需验证进程退出后的控制权行为 |
| 包应用/启动器入口的有限适配 | EXE 名与窗口进程不同，部分软件用应用标识启动 | 只覆盖实际需要的软件，避免通用启动器平台 |
| 第二次启动通知已有实例显示 | 让桌面快捷方式能够唤醒托盘界面 | 小功能，复用现有单实例边界并核对本机权限 |

| 需要提权的登录启动方案 | HKCU Run 不足以保证控制管理员原厂程序 | 单独设计并说明权限行为，不能在“清理”中自动创建高权限任务 |

不建议本轮加入遥测、云配置、SignalRGB、通用插件架构、硬件底层协议或框架迁移。下一步建议先完成阶段 1，再处理 SDK 生命周期；本轮审查不需要用户操作硬件。
